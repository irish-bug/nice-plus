# AGENTS.md

Instructions for AI agents (Claude, Codex, Copilot, Cursor, Gemini, or any other) that are
helping review or contribute to NICE Plus. Human contributors should follow the same rules.

NICE Plus is an open, **draft** extension of the NIST NICE Workforce Framework for OT/ICS
cybersecurity roles. It is meant to be imperfect, and reviews from many people and many
agents are exactly what it needs. The most valuable contributions are often not new
content but **finding what is wrong**:
- a bad citation
- a statement in the wrong role
- a missed NICE statement
- a better source

Read `README.md` (data model, roles) and `CONTRIBUTING.md` (rules) before you start.

## Non-negotiable rules

1. **Never fabricate a source, locator, ID or quote.**
   - Only cite documents you actually opened in this session.
   - Set `locator_status: "verified"` only if you read the source text at that locator.
   - If you could not open or check something, say so and use `to-verify`.
   - An honest "I couldn't verify this" is far more useful than a confident guess.
2. **Look up IDs; never recall them.**
   - NICE IDs come from `data/nice/v2.2.0/`.
   - ATT&CK for ICS IDs come from `data/attack-ics/v20.1/techniques.json`.
   - ATT&CK v20 renumbered several techniques, so IDs from memory are often wrong.
3. **NICE text is verbatim.** Never edit NICE statements or roles. Propose a plus
   statement that refines one instead.
4. **No copyrighted standards text.** ISA/IEC 62443, IEC 62264, IEC 61131-3 and similar
   standards are cited by part and clause and paraphrased. Don't paste their text into
   issues or files.
5. **Choose statements on merit.** A statement belongs in a role because the job needs it,
   not because training or tooling happens to cover it.
6. **A human is responsible.** The person running you should read what you produce before
   it is submitted. Say in every issue and PR that it is AI-assisted, which agent or model
   you are, and what sources you checked.

## How to contribute without stepping on others

Many agents may be working on this repo at once.
- **Search open issues and PRs first.** If your finding is already reported, add evidence
  to that issue instead of opening a new one.
- **One finding per issue, one topic per PR.** Small, specific reports are easy to review
  and merge.
- **Claim larger work before starting** (e.g. drafting a stub role) by commenting on its
  issue, or opening one.
- **New plus IDs:** in a PR, use the next free number. Two parallel PRs may pick the same
  number, so maintainers may renumber before merging. Once merged, an ID is permanent.
- **Prefer issues for judgments** (flags, wording, role scope) and **PRs for mechanical
  fixes** (a verified locator, a typo, a broken citation).

## Where things are

| You want to | Edit |
|---|---|
| Add or fix a plus statement | `plus/statements.json` |
| Change a role's statements, flags or open questions | `plus/roles/PR-OT-###.json` |
| Change a competency area (e.g. Cyber-Informed Engineering) | `plus/competency_areas.json` |
| Add a source | `sources/registry.json` |
| Anything in `data/` or `export/` | Don't. These are generated by `make`. |

Before opening a PR:

```sh
pip install -r requirements-dev.txt
make build   # must pass: rejects ID clashes, unknown sources, revoked ATT&CK IDs, duplicates
make check   # JSON Schema validation
```

Commit the regenerated `export/` files with your change.

## Statement style

Follow NICE's style:
- tasks are imperative ("Maintain backups of …")
- knowledge is "Knowledge of …"
- skills are "Skill in …"

Keep each statement to one idea. Add examples in "(e.g., …)" only when they make it
clearer. Statements should be general OT unless they are sector-specific; then set
`ot_context.sectors`.
