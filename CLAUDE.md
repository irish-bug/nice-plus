# CLAUDE.md

Guidance for Claude Code in `nice-plus`. Also follow `AGENTS.md`, the rules for every AI
agent contributing here. `README.md` covers the data model, ID rules and the export contract.
`CONTRIBUTING.md` covers how changes are proposed. This file covers how to work here.

Private context (timelines, private sources) lives in `CLAUDE.local.md`, which is
gitignored. This repo is meant to be public: never copy private context into tracked files.

## What this is

NICE Plus is an open, citable extension of the NIST NICE Workforce Framework for OT/ICS
cybersecurity roles. NICE does not cover OT/ICS/SCADA roles well. NICE Plus uses NICE's
structure and IDs and adds the OT roles and TKS statements NICE lacks, so training can be
planned from a job role.

It is expected to be imperfect. The aim is a useful, clearly sourced starting point that
others can correct. Make flaws easy to find:
- honest statuses
- open questions
- `to-verify` locators

It feeds the role-led planning path of the ottobotto cyber range: role → work role + TKS →
learning objectives → modules → labs → exercise. This repo owns the export contract
(`schema/role-export.schema.json`, `schema_version`). Change it deliberately, bump the
version, and record the change in the README and CHANGELOG.

## Hard rules

- **Never present nice-plus content as a NIST product.** Plus roles are
  `stub | draft | reviewed`, plus statements are `draft | reviewed`, and every export
  carries the draft notice.
- **NICE text stays verbatim and versioned.** Never edit NICE statement or role text,
  including stray whitespace (e.g. `T2028` ends with a space). Use `nice_version`.
- **Separate namespaces.** Plus IDs never reuse or resemble NICE IDs:
  - plus statements: `P[TKS]-OT-####`
  - plus roles: `PR-OT-###`
  - NICE categories OG/DD/IO/PD/IN are taken, so no plus prefix may start with them.
  - IDs are never renumbered or reused. A withdrawn item keeps its ID.
- **ATT&CK for ICS IDs only go in `attack_ics` fields.** They share the `T####` shape with
  NICE task IDs. v20 renumbered several techniques (e.g. T0855→T1692.001), so never trust
  a technique ID from memory. `build.py` checks every one.
- **Cite everything.** Every plus statement and role cites a source in
  `sources/registry.json`.
  - `locator_status: verified` only when you have read the source at that locator.
  - `support: paraphrase` only when the source actually says it. Otherwise use `related`.
  - Mark inferred judgments "Inferred:".
- **No copyrighted standards text.** ISA/IEC 62443, IEC 62264 (ISA-95), IEC 61131-3 and
  similar are cited by part (and clause once verified) and paraphrased. We hold no copy of
  62443, so its clauses are `to-verify`.
- **Choose statements by relevance to the job.** Sweep all NICE statements; never pick
  statements because a coverage source (e.g. puzzle tags) uses them. Coverage sources are
  examples. Report coverage by basis (inherited / added-nice / plus).
- **Coverage imports carry tags only.** Import paths, statement tags, objectives and
  release IDs. Never import puzzle text, hints or answers, and never record private server
  URLs.
- **Roles are general OT roles.** Sector-specific statements carry
  `ot_context.sectors`; an empty list means any sector. PR-OT-001 is the one deliberate
  manufacturing specialization.

## Layout and commands

```
sources/   pristine copies + provenance; registry.json = every citable source
schema/    nice-plus.schema.json (model), role-export.schema.json (ottobotto contract)
scripts/   import_nice.py, import_attack_ics.py, import_cyberfire.py, build.py, check_schema.py, common.py
data/      generated by importers; never hand-edit
plus/      hand-authored: statements.json, roles/*.json, optional coverage_map.json (inferred)
export/    generated by build.py: index.json, roles/<id>.json
```

- `make`: import everything, validate, build exports. It skips the Cyber Fire import if the
  sibling repo is missing.
- `make build`: validate and export from committed data. Needs no network or siblings.
- `make check`: JSON Schema validation. Needs `requirements-dev.txt`; use a venv, not the
  system Python.
- Output is deterministic. After a change, rebuild and confirm the diff is only what you
  intended.
- `build.py` exits non-zero on any rule violation. Fix the data; never weaken a check to
  get past it.

### Adding or extending a role

1. **Stub:** title, description, category, `related` NICE roles, citations,
   `open_questions`.
2. **Draft:**
   - Use `inherit` (`default_flag` plus `core` / `additional` exception lists) for a NICE
     role it specializes.
   - Use `add_nice` for other relevant NICE statements, each with an "Inferred:" rationale.
   - Use `add_plus` for plus statements. Reuse existing plus statements before writing new
     ones.
3. **Writing new plus statements:**
   - Check every locator against the source text. Keep source PDFs in the session
     scratchpad, not the repo.
   - Check ATT&CK IDs against `data/attack-ics/`.

## Sources

- **NICE Framework Components v2.2.0** (released 2026-04-28 per the NIST change log). Check
  nist.gov/nice for newer releases.
- **MITRE ATT&CK for ICS v20.1.** Keep MITRE's notice (`sources/attack-ics/LICENSE.txt`).
- **Cited but not held:**
  - NIST SP 800-82r3 and NISTIR 8183r1 (locators are section + PDF page index)
  - DOE/INL Cyber-Informed Engineering
  - Top 20 Secure PLC Coding Practices (locators are practice numbers)
  - ISA/IEC 62443

## How to work

- Plan first: propose roles and data-model changes and check with the user before building.
- Commit or push only when asked. Work on a branch and merge through a PR.
- HTML is the preferred hand-out format. Pages are self-contained:
  - inline CSS and JS, no CDNs
  - light and dark themes
  - work offline
